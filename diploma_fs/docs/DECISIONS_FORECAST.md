# Принятые решения: ветка research/forecast

Журнал решений по новой теме диплома. Каждое решение: **что решили → почему → где в коде/документах**.
Если решение меняется — добавляется новая запись с датой, старая не стирается.
Критерии экспериментов — `docs/FORECAST.md` (критерий C), формат отчёта — `docs/REPORT_FORMAT.md`.

## 1. Тема и рамки (29.09.2026)

| № | Решение | Почему | Где |
|---|---|---|---|
| 1.1 | **Тема:** прогноз энергопотребления предприятия — временные признаки + отбор факторов для CatBoost (вариант A из ADR-001) | прежняя тема (выбор формы признаков) почти не даёт роста качества; здесь рост заметный (на модельном заводе R² 0,52 → 0,95), есть прямая связь со статьёй руководителя | `docs/ADR-001.md` |
| 1.2 | **Главный вопрос:** насколько временные признаки повышают точность прогноза и сколько из них можно отбросить без потери качества | одна понятная история для защиты | `docs/FORECAST.md` |
| 1.3 | Работа ведётся в ветке `research/forecast` (от `research/real-data`); `main` и `app/` не трогаем | не ломаем прежние результаты | — |
| 1.4 | Прежняя тема (формы признаков, ACE, Бокс–Кокс) уходит в приложение | результат слабый, но код и выводы пригодятся | `research/real-data` |
| 1.5 | Тему нужно согласовать с руководителем (А. С. Сысоев) | он автор статьи об отборе факторов для CatBoost | **открыто** |

## 2. Постановка задачи

| № | Решение | Почему | Где |
|---|---|---|---|
| 2.1 | **Горизонт прогноза — 1 час** (для Steel = 4 шага по 15 мин) | практичный краткосрочный прогноз; задаётся в реестре, меняется флагом `--horizon` | `fsx/registry.py` → `horizon` |
| 2.2 | **Два режима:** «прогноз» (основной — известно только прошлое) и «виртуальный датчик» (текущие показания датчиков известны) | честное сравнение с литературой: большинство работ по Steel решают именно задачу «виртуального датчика» | `--mode forecast / virtual` |
| 2.3 | **Нет утечки будущего:** признак для момента t строится только из данных до t − h; сдвиги считаются по времени, а не по номеру строки | иначе метрики завышены; сдвиг по строкам ломается на пропусках в ряду | `fsx/lags.py`, `check_no_leak`, `tests/test_lags.py` |
| 2.4 | Известными заранее считаются только календарь и колонки `known_ahead` (Steel: секунды от полуночи, тип дня, день недели) | их можно знать на час вперёд без измерений | `fsx/registry.py` |
| 2.5 | Тип нагрузки Steel (`Load_Type`) считается **не** известным заранее и берётся с лагом | консервативно; если по данным окажется, что он жёстко привязан к часу, — перенести в `known_ahead` | **проверить на данных** |
| 2.6 | **CO₂ в Steel удалён** как утечка | выбросы считаются из самого потребления: модель видела бы ответ | `drop` в реестре |

|---|---|---|---|

## 4. Проверка и статистика

| № | Решение | Почему | Где |
|---|---|---|---|
| 4.1 | Ряд делится на 10 отрезков → **9 проверок «прошлое → будущее»**; зазор между обучением и тестом ≥ max(1% ряда, h) | модель никогда не учится на будущем | `fsx/forecast.py` → `forward_splits` |
| 4.2 | Первая неделя ряда (для недельного лага) выбрасывается **для всех наборов одинаково** | все модели сравниваются на одних и тех же строках | `warmup_` |
| 4.3 | Главная метрика — **MAE в кВт·ч**; дополнительно R², RMSE, MAPE (по ненулевым), WAPE, время, число признаков | MAE понятна без формул; у Steel бывают нули, MAPE на них ломается | `fsx/models.py` → `metrics` |
| 4.4 | Сравнения — тест Уилкоксона по 9 проверкам, поправка Холма; рейтинг — Фридман + критическая разница Неменьи | как в прежней части работы, переиспользуется | `scripts/report_forecast.py` |
| 4.5 | **Критерии E1–E4 зафиксированы до прогона** на реальных данных | чтобы не подгонять выводы под результат | `docs/FORECAST.md`, критерий C |

## 5. Модели

| № | Решение | Почему | Где |
|---|---|---|---|
| 5.1 | Сравниваем: наивный «как час назад», наивный «как вчера», **GLM** (линейная регрессия; Ridge — её вариант с регуляризацией), **XGBoost**, **CatBoost** | наивный прогноз — нижняя планка; GLM — как в опубликованных работах по Steel; два бустинга — основной класс моделей | `fsx/models.py` (GLM и XGBoost — **добавить**) |
| 5.2 | CatBoost: 500 деревьев, глубина 6, CPU | укладывается в ноутбук | `CB_DEFAULT` |
| 5.3 | Если CatBoost не установлен — вместо него HistGradientBoosting с пометкой `hgb_fallback`; **такие результаты в диплом не идут** | подмена видна в отчёте, одно не выдаётся за другое | `make_catboost` |
| 5.4 | Настройка Optuna (≤ 30 попыток) — только на обучающей части **первой** проверки, потом параметры замораживаются | будущие отрезки не влияют на параметры; экономия времени | `tune_catboost`, `--tune` |

## 6. Отбор признаков

| № | Решение | Почему | Где |
|---|---|---|---|
| 6.1 | Три ранжирования CatBoost — встроенная важность, перестановки, SHAP — и **одно общее правило** «сколько оставить»: наименьший топ-k%, чей MAE не хуже лучшего более чем на 1% | сравниваются именно ранжирования, а не разные правила отсечки | `fsx/selectors/catboost_sel.py` |
| 6.2 | Внутренняя проверка отбора — последние 20% обучающих данных **по времени** | случайная проверка у рядов завышает качество | там же |
| 6.3 | Для сравнения также RFE, Boruta, групповая важность и **метод Сысоева — оригинал из статьи и исправленная версия** | E4 — место метода руководителя среди других | `DEFAULT_SELECTORS` |
| 6.4 | Группа признака для Сысоева = всё до `__` (например, «все короткие лаги потребления») | метод удаляет «модификации одного фактора»; для лагов это группа однотипных лагов | `LagFE.groups` |
| 6.5 | **Пустой отбор** оценивается как прогноз средним значением и честно попадает в конец рейтинга | его нельзя молча выбрасывать (у статейного метода Сысоева это частый случай) | `fsx/forecast.py` |
| 6.6 | Методы `cb_*` не входят в `--method all` старого стенда | состав прежних прогонов не меняется | `scripts/run.py` |

## 7. Формат отчёта (согласован и подтверждён 29.09.2026)

| № | Решение | Где |
|---|---|---|
| 7.1 | Отчёт читается без знания кода: **ни одного кода без расшифровки**, значения категорий переведены, у чисел единицы, статистика словами | `docs/REPORT_FORMAT.md` |
| 7.2 | Структура: 0 Итог · 1 Задача · 2 Вход (паспорт, **первые 5 строк** с русскими заголовками, расшифровка столбцов) · 3 Признаки («одна строка глазами модели») · 4 Модели · 5 Выход (факт и прогнозы) · 6 Результат и сравнение · 7 Выводы и словарик | там же |
| 7.3 | Технические имена — только в приложении, один раз | там же |
| 7.4 | Отчёт — Markdown + PDF; образец (числа условные) строит `scripts/make_report_sample.py` | `docs/REPORT_SAMPLE.pdf` (не в git, создаётся скриптом) |
