# Гипотезы о настройке Optuna (ветки research/hpo-*)

Вопрос: когда настройка гиперпараметров через Optuna реально улучшает модель на **будущих** данных,
а когда улучшение видно только на проверочной выборке?

## Как устроены ветки

| Ветка | Что в ней | Чем отличается от базы |
|---|---|---|
| `research/hpo-base` | общий стенд, базовая настройка Optuna, три датасета | — |
| `research/hpo-trials` | гипотеза «Число попыток» | только число попыток: 10 / 25 / 50 / 100 |
| `research/hpo-early-stopping` | гипотеза «Ранняя остановка» | только выборка для ранней остановки |

Правило: **одна ветка меняет одну вещь**. Всё остальное (данные, признаки, модели, внешняя проверка, seed) одинаково.

## Базовая настройка Optuna

Повторяет `tuning/run_optuna_model.py` основного проекта:

| Параметр | Значение |
|---|---|
| проверочная выборка | случайные 20% обучающих строк (seed 42) |
| ранняя остановка | 50 раундов, по той же проверочной выборке |
| способ перебора | TPE, seed 42, multivariate, стартовых случайных попыток max(5 × число параметров, 20) |
| попыток | 50 |
| итоговая модель | модель лучшей попытки (обучена на 80% обучающих строк) |
| пространства поиска | как в `tuning/search_spaces.py` (XGBoost, LightGBM, CatBoost) |

Следствие стартовых попыток: у XGBoost и LightGBM по 9 параметров, значит первые 45 попыток из 50 — случайные,
TPE включается только в конце (у CatBoost — после 30-й). Это свойство базовой настройки, мы его не меняем.

## Данные и модели

- Датасеты: Tetouan (потребление города), Steel (сталелитейный завод), Appliances Energy (дом с датчиками).
  Последние 10 000 строк каждого, прогноз на 1 час вперёд, признаки — только из прошлого (`fsx/lags.py`).
- Модели: «как час назад» и линейная (Ridge) — опорные; sklearn-бустинг (HGB), LightGBM, XGBoost, CatBoost —
  каждая в двух видах: **стандартная** (параметры библиотеки по умолчанию) и **настроенная Optuna**.
- Внешняя проверка: ряд режется на 10 блоков, тест — последние 5 блоков по очереди, обучение — только то, что раньше.
  Тест не участвует в выборе настроек; ошибка на нём пишется для каждой попытки только для анализа.

## Что измеряем

| Показатель | Смысл |
|---|---|
| изменение к стандартной | ошибка настроенной модели на будущем / ошибка стандартной − 1 (минус — настройка помогла) |
| хуже стандартной | в скольких случаях настройка сделала хуже |
| изменение при обучении на всех данных | те же настройки и число деревьев, но обучение на всех обучающих строках, как у стандартной модели: показывает, чего стоят сами настройки, без потери 20% данных |
| будущее против проверки | реальная ошибка / ошибка, которую видела Optuna − 1 (большой плюс — самообман) |
| связь проверка ↔ будущее | корреляция Спирмена по всем попыткам: предсказывает ли проверка будущее |
| потеря к лучшей попытке | на сколько выбранная попытка хуже лучшей из сделанных |

## Запуск

```bash
pip install -r requirements-extra.txt              # catboost, xgboost, lightgbm, optuna
python scripts/download_data.py tetouan steel appliances
python scripts/run_hpo.py --experiment base --quick                 # проверка, несколько минут
python scripts/run_hpo.py --experiment base                         # база
python scripts/run_hpo.py --experiment h_trials                     # ветка research/hpo-trials
python scripts/run_hpo.py --experiment h_early_stopping             # ветка research/hpo-early-stopping
python scripts/report_hpo.py --experiment h_trials                  # -> docs/HPO_REPORT_h_trials.md
```

Контроль (не отдельная гипотеза): любой эксперимент можно повторить с проверкой по времени —
`--val-scheme time --name <имя>_time`. В предварительной пробе именно схема проверки давала самый большой эффект.

Оценка времени на ноутбуке (N95): база ≈ 3 датасета × 3 модели × 5 отрезков × 50 попыток ≈ 2 250 обучений, несколько часов;
`h_trials` — вдвое дольше, `h_early_stopping` — втрое. Запускать на ночь; можно по одному датасету: `--dataset tetouan`.
