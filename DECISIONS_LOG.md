## 8. Рефакторинг под sklearn Transformer (2026-09-09)

- **Контекст:** Feature engineering выполнялся в свободных функциях (медианы, `PowerTransformer`, `RBFSampler`) и **фитился на всём датасете ДО сплита** → Data Leakage: модель «видела» тестовые данные при обучении, метрики были завышены и нечестны.
- **Решение:** Переписать обработку в класс `AdvancedFeatureTransformer` (наследник `BaseEstimator`, `TransformerMixin`). `.fit()` строго на `X_train`, `.transform()` применяет знания (медианы, стили, фиты) к `X_test` без подглядывания. В `experiments/run_experiment.py` сплит теперь строго ПЕРЕД обработкой признаков. SHAP-отбор — только на `X_train`.
- **Причина:** Требование честности оценки — тестовая выборка не должна влиять на обучение. Это стандарт sklearn-пайплайнов и обязательное условие для любой серьёзной комиссии.
- **Результат:** ✅ Дало — главная победа проверки: полное отсутствие утечек данных, код выглядит как работа Middle/Senior Data Scientist.

## 6. Структура проекта (2026-09-07)

- **Контекст:** Код был «набором скриптов»: модули импортировали друг друга напрямую, оценка дублировалась в 3 местах.
- **Решение:** Чистая модульная структура: `app/` (Streamlit UI), `src/` (core ML), `src/common/` (config, artifacts, schemas, logging, cv_runner), `tuning/` (Optuna), `configs/`, `experiments/`, `orchestration/`, `utils/`, `Final/`.
- **Причина:** Принцип «модуль решает одну задачу», запрет прямых импортов между модулями, единая точка оценки через `cv_runner`.
- **Результат:** ✅ Дало — поддерживаемый код, чистое разделение ответственности.

## 5. SHAP-отбор признаков против мультиколлинеарности (2026-09-05)

- **Контекст:** Feature engineering раздувал датасет до 173 признаков; многие коррелировали между собой → неустойчивость модели.
- **Решение:** Модифицированный алгоритм Сысоева — SHAP-отбор для устранения мультиколлинеарности (173 → 8 некоррелированных признаков).
- **Результат:** ✅ Дало — SHAP улучшает R² при мультиколлинеарности: FE(173)=0.8266 → SHAP(8)=0.8360 (+0.94%), те же параметры FE→SHAP: 0.8388 (+1.21%). На изначально некоррелированных признаках эффекта нет (−0.4%).

## 1. Честное сравнение Grid Search vs Optuna (2026-09-01)

- **Контекст:** Оптимала сравнивали с Grid некорректно: Optuna с непрерывным пространством (`suggest_int`/`suggest_float`) находила значения, которых нет в Grid (`learning_rate=0.073` vs `0.1`) — это сравнение «яблок с апельсинами».
- **Решение:** Заставить Optuna использовать ТОЛЬКО `suggest_categorical` с теми же значениями, что и Grid Search.
- **Результат:** ✅ Дало — выяснили правду:
  | Модель | Grid | Optuna (categorical) |
  |--------|------|----------------------|
  | XGBoost | 0.8452 | 0.8452 (одинаково) |
  | LightGBM | 0.8411 | 0.8392 (Grid чуть лучше) |
  | CatBoost | 0.8358 | 0.8358 (одинаково) |

  **Вывод:** Optuna НЕ превосходит полный перебор по качеству при одинаковом пространстве; её преимущество — **скорость** (100 trials против 1000+ комбинаций, в 9–11x быстрее).
