## Компромиссы при внедрении улучшений в ваш ML-пайплайн

Ниже — каждое предложение с **компромиссами** (что выигрываем и чем платим).

---

### 1. Кросс-валидация внутри Optuna

| Выигрыш | Потери |
|---------|--------|
| Честная оценка качества, защита от переобучения под конкретный split | Каждый trial обучает модель **K раз** (обычно 5) → время растёт в 5 раз |
| Более стабильные гиперпараметры | Сложность кода: нужно передавать CV-схему в objective |

> **Компромисс:** Стабильность vs Время расчёта

---

### 2. Pruning (ранняя остановка)

| Выигрыш | Потери |
|---------|--------|
| Бесперспективные trials отсекаются рано → экономия времени (до 50-70%) | Нужно добавить `get_pruner_callback()` и поддерживать промежуточные метрики |
| Можно запускать больше trials за то же время | Некоторые модели могут «не успеть» показать потенциал, если pruner слишком агрессивный |

> **Компромисс:** Скорость vs Риск отсечь потенциально хороший trial

---

### 3. Оптимизация предобработки через Optuna

| Выигрыш | Потери |
|---------|--------|
| Автоматический выбор: масштабировать или нет, какое кодирование использовать | Пространство поиска растёт → нужно больше trials для сходимости |
| Пайплайн становится полностью автоматическим | Код сложнее: нужно оборачивать предобработку в функцию с параметрами |

> **Компромисс:** Автоматизация vs Сложность и время поиска

---

### 4. MLflow (логирование)

| Выигрыш | Потери |
|---------|--------|
| Все метрики, параметры, артефакты в одном месте. Можно сравнивать эксперименты | Дополнительная инфраструктура: нужно поднять MLflow server (или использовать локально) |
| Воспроизводимость экспериментов | Плюс папка `mlruns/` в проекте, нужно не забывать логировать |

> **Компромисс:** Удобство управления экспериментами vs Дополнительная инфраструктура

---

### 5. Docker

| Выигрыш | Потери |
|---------|--------|
| Пайплайн работает одинаково на любой машине (Linux, Windows, Mac, сервер) | Нужно изучать Docker, писать Dockerfile, собирать образ |
| Лёгкий деплой на любой облачный сервис | Образ может быть тяжёлым (1-2 GB) из-за зависимостей |

> **Компромисс:** Портативность vs Порог входа и размер образа

---

### 6. API (FastAPI) отдельно от Streamlit

| Выигрыш | Потери |
|---------|--------|
| Модель можно вызывать из любого приложения (телеграм-бот, фронт, другой сервис) | Нужно поддерживать два сервиса: API + Streamlit |
| Streamlit остаётся только демо/интерфейсом | Усложнение архитектуры: нужно решать, как они общаются |

> **Компромисс:** Гибкость vs Сложность архитектуры

---

### 7. NGBoost / PGBM (вероятностные бустинги)

| Выигрыш | Потери |
|---------|--------|
| Модель возвращает не точку, а распределение → можно оценить **уверенность** прогноза | Скорость обучения ниже, чем у LightGBM |
| Интересный эксперимент: сравнить с детерминистическими моделями | Требуют больше времени на настройку, меньше документации |

> **Компромисс:** Дополнительная информация (уверенность) vs Скорость и простота

---

### 8. Evidently AI (мониторинг дрейфа данных)

| Выигрыш | Потери |
|---------|--------|
| Можно отслеживать, меняются ли данные после деплоя (data drift, target drift) | Нужно хранить референсные данные и регулярно прогонять проверки |
| Автоматические отчёты о качестве во времени | Дополнительный сервис / скрипт в проекте |

> **Компромисс:** Надёжность в продакшене vs Сложность поддержки

---

### 9. DVC (версионирование данных)

| Выигрыш | Потери |
|---------|--------|
| Данные версионируются, можно откатиться к старой версии. Данные в Git не хранятся (только ссылки) | Дополнительная команда `dvc pull`, нужно хранить remote storage (S3, Google Drive) |
| Воспроизводимость экспериментов | Команда `git pull` теперь ещё и `dvc pull` → два шага вместо одного |

> **Компромисс:** Контроль версий данных vs Дополнительные инструменты и storage

---

### 10. GitHub Actions (CI/CD)

| Выигрыш | Потери |
|---------|--------|
| При пуше в репозиторий автоматически запускаются тесты, а иногда и обучение | Настройка требует времени и понимания YAML/CI |
| Автоматическая проверка, что код не сломался | Бесплатные лимиты: 2000-3000 минут в месяц для GitHub Actions |

> **Компромисс:** Автоматизация vs Сложность настройки и лимиты

---

## 📋 Итоговая таблица компромиссов

| Улучшение | Выигрыш | Плата |
|-----------|---------|-------|
| Кросс-валидация | Честность оценки | Время × K |
| Pruning | Скорость | Риск отсечь хороший trial |
| Оптимизация предобработки | Полная автоматизация | Сложность кода |
| MLflow | Управление экспериментами | Дополнительная инфраструктура |
| Docker | Портативность | Размер образа, порог входа |
| FastAPI API | Гибкость | Сложность архитектуры |
| NGBoost/PGBM | Интервалы уверенности | Скорость, документация |
| Evidently AI | Мониторинг дрейфа | Дополнительный сервис |
| DVC | Версионирование данных | Remote storage |
| GitHub Actions | CI автоматизация | Лимиты времени |

---

## 🎯 Короткий ответ для руководителя (если спросит)

> *«Каждое улучшение даёт выигрыш в определённой области, но требует либо дополнительного времени вычислений, либо усложнения инфраструктуры. Например, кросс-валидация делает оценку честнее, но замедляет обучение в 5 раз. Docker даёт портативность, но требует настройки. Главный компромисс в ML-проектах — между качеством/автоматизацией и сложностью/временем.»*
